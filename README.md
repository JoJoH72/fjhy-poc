# 福建海运集团POC · 差旅费 AI 智能审核

领域知识资产（4 个二级菜单，三元本体收在「本体工场」下）+ 报账单 AI 审核端 + 系统组（大模型配置、系统自检）。

**AI 结论是参考，不阻断流程；闸门在人工复核。**
这不是说法上的谦虚，是实测结论：`FJPG-BX2610130821` 在 2026-10-13 17:25:03
得到「AI审核不通过」，17:35:41 仍进入共享审核并由人工给出退回理由。

## 怎么跑起来

### 最省事：双击 `启动.bat`

```
启动.bat              # 起数据库 → 起后端 → 起前端 → 开浏览器
启动.bat 8010 5174    # 指定端口
停止.bat              # 只停本项目的服务，数据库容器不动
```

脚本会：服务已在跑就先停再起；首次运行自动建表、装载本体与规则资产、
灌样本与演示数据、跑一轮审核；起完做一次接口自检再开浏览器。

**端口被占时不会乱杀。** 占着端口的未必是本项目的东西——
本机 8000 上就有一个别的工程的服务（PID 25492）。
脚本会核对进程命令行，只停本项目自己的；别人的一律不碰，自动往后找空端口并告知。
实测输出：

```
!!  后端 端口 8000 被**别的程序**占用（PID 25492 python.exe），不动它，试下一个端口
!!  后端 端口 8000 被占，改用 8001
OK  后端 8001 · 前端 5173
...
OK  规则 82 条 · 可编译 37 · 执行集 12
OK  数据库 57 表 · 迁移 13 · 脱敏 on · 审计一致
OK  单据 59 张（真实 40 · 演示 19）
```

日志在 `var/log/`，PID 在 `var/run/`。

下面是手动分步跑，排查问题时用。

### 1. 数据库

```bash
docker compose up -d                 # 起 fjhy-poc-sdafi-pg（127.0.0.1:55460）
```

容器与库名都带 `fjhy-poc` 前缀，**不碰本机已有的 `fjpg_audit_pg` /
`sdafi-base-pg` / `tf_ai_pg`** ——它们属于别的工程，往里加表会动到对方的迁移链。

### 2. 后端

```bash
cd 服务端
python -I db/migrate.py              # 建表（13 个迁移）
python -I app/ontology/loader.py     # 装载本体（本体_v0.1.yaml → 库）
python -I app/rules/loader.py        # 装载规则资产（82 条规则 + 4 张查找表）
python -I app/llm/presets.py         # 装载国内厂商预置（11 条）
python -I app/demo/seed.py           # 装载客户真实样本（40 张单）
python -I app/demo/generator.py      # 生成带已知缺陷的演示数据（19 张单）
python -I -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

启动时会做两道契约校验（规则资产 20 项 + Agent 配置 48 项），
**任一不过就拒绝启动**。不是「启动后报警」——启动后报警的系统会在报警被忽略的
情况下继续给出错误的审核结论。

跑一轮审核：

```bash
python -I -c "import sys,os; sys.path.insert(0,os.getcwd()); \
from app.runtime.orchestrator import Orchestrator; \
Orchestrator().startup().heartbeat_once(limit=200)"
```

### 3. 前端

```bash
cd 前端
npm install
npm run dev                          # http://127.0.0.1:5173
```

后端端口被占用时（本机 8000 就被别的进程占着）：

```bash
FJHY_API_TARGET=http://127.0.0.1:8010 FJHY_WEB_PORT=5174 npm run dev
```

### 4. 验一遍

```bash
cd 服务端 && python -I -m pytest tests/ -q      # 179 项
cd 前端   && npx vue-tsc --noEmit && npx vitest run   # 类型 + 12 项
python -I 规则资产/validate.py                   # 规则资产一致性
```

## 几个必须知道的口径

**「可编译 37」与「执行集 12」是两件事。**
前者是规则资产层面（口径清楚、阈值可信、决策表齐备）；后者是手上有没有数据。
混成一个数，产品缺口和取数缺口就分不清了。

**「待人工」不等于「通过」。**
把它算进通过，报告上就会出现「本单规则全部通过」，而实际有十几条根本没跑。
报告里四个数并列：候选 / 执行 / 命中 / 待人工，外加「未执行」单列一节。

**误报与漏报分开计，不合成准确率。**
漏报放过风险；误报把正常单据判成问题件，审核岗很快就不再信任这套系统。
另外「仅待人工」单列——它不是误报，是没把握。

**40 张真实样本里没有违规案例。**
它们全是审批完成、人工放行的合规单据。在上面跑出「0 命中」只证明**没误拦**，
证明不了抓得住。检出能力用 `app/demo/generator.py` 的 19 张带已知缺陷的
演示数据验，检出矩阵在 `服务端/tests/test_detection.py`。

**演示数据一眼可辨**：单据号带 `FJHY-DEMO-` 前缀、`is_demo=TRUE`、
摘要带「【演示数据】」、核算主体用 `DEMO-ORG-*`（与真实主体隔开，
否则拆单检测会把两边算在一起）。

## 两个该问客户的数

1. **日均单量与月末峰值。** 直接决定「无 Redis 无 MQ、用 PG 表当队列」
   这个架构成不成立。样本只有 40 张，推不出量级。
2. **海运集团《事权审批单》是否适用于财智分公司。** 审核要点 1.3.9.1 的主语是
   「海运集团」，而 40 张样本的核算主体全是「财智分公司」。
   适用则 28 张金额 ≥1000 的单全部缺附件；不适用则一条都不该报。
   28 条误报与 28 条漏报之间，只能由业务侧定（缺口 G-12）。
