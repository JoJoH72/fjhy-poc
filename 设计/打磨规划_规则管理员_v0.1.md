## 一、四步工作流主干体检

先给总结论，再逐环节证据。**四步里「上传」和「发布」是通的，「抽取」「审定」两步的后端链路完好、但操作入口在 10-27 的死代码退役中随五个旧页（Extract/RuleOnto/BizOnto/ProcessOnto/Workshop）一起被物理删除，替代页没有把交互工作流搬过来——这是本角色当前最大的结构性断点，也是客户「冲突标注点不开」投诉的根源。**

| 步骤 | 结论 | 一句话 |
|---|---|---|
| ① 传文件 | **通** | 上传→自动扫描→扫描件自动视觉转写，实测 16 份在库、台账齐全 |
| ② 跑 AI（抽取） | **断（UI）** | 后端四 Agent 链完好（92 条款/21 草稿/40 明细），但「增量抽取」按钮已随旧页删除，navTree 注释宣称的「文件库+抽取合并」实际没合并进来 |
| ③ 审定 | **断（UI）** | 草稿/明细审定 API 全活（实测 26 待审/7 采纳/7 驳回），审定页没了；冲突裁决 UI 同样没了 |
| ③' 冲突标注 | **断** | 客户投诉确认：标注在、点不开（无头实测可点元素=0）；冲突台账管线在但表现数据为空 |
| ④ 发布 | **通** | 冻结→签字→切当前→回滚全链实测可用；小缺口：从未有 published 版本，引擎跑在草稿兜底上；discard/送审两个动作漏埋 op_log |

### 1.1 上传一份新制度文件后，抽取出了什么？

**上传链路本身：通。** 实测（接口 + DocLib.vue 代码路径）：

- 上传 → `doclib.save_uploads`（落盘按 sha256 去重、同名另存、七态逐份判定）→ 自动 `scan(root_ids, parse=True)`（六态解析、指纹、变化台账）→ 需 OCR 的 pdf 自动走视觉转写（DocLib.vue `afterUpload` 里对 `parse_state==='需OCR' && ext==='.pdf'` 的新上传文件自动调 `dlVisionOcr`）。实测在库 16 份（9 pdf / 3 xlsx / csv / docx / md / txt），已解析 11、需OCR 5，全部 origin=上传。
- 「待抽取」口径 `/api/doclib/pending-extract` 实测 total=0（16 份都被 mark_extracted 过）。

**但「上传即抽取」（客户待办 #8）没有发生，也没有入口。** 证据：

1. navTree.ts L48 注释写着「制度文件页=文件库+抽取合并（客户待办#8『上传后直接同步抽取』）」，但 DocLib.vue 通篇没有 `api.exRun` 调用（全仓 grep `.vue` 文件，`exRun/exIncremental/exProgress/exStats/exDrafts` 的调用点为 **0**，唯一残留是 api.ts 里的类型与封装）。上传后的自动动作只有视觉转写，切条款/AI 草稿不会跑。
2. 旧 Extract.vue（git 5783cbc）里的「增量抽取（N 份 · 含 AI 草稿，出网计费）」按钮、增量范围预览、四 Agent 进度面板——这些交互在合并时全部丢失，redirect 到 /asset/docs 后只剩文件库五页签。
3. 后端抽取链完好且数据在：`/api/extract/stats` 实测 clauses=92、candidates=40、drafts=21；`/api/extract/details/stats` 实测 total=40（AI草稿 20 + 场景拆条 14 + 列映射 6），adopted=7、**into_onto=0**。
4. 老栏目二的 `extract_candidate` 表（asset.py 的 /api/asset/extract/candidates）实测 total=0、tasks=0——这是 pre-doclib 时代的遗留资产，现行链路的真实草稿表是 `doclib_draft` 和 `doclib_rule_detail`。规划引用数据源时不要用错表。

### 1.2 审定动作在哪？审定后进规则库了吗？

**审定机制在，页面没了；「进规则库」这一步从未通过 UI 走通过。**

- 草稿审定：`POST /api/extract/drafts/{id}/review`（采纳/驳回/撤回，驳回必填原因，reviewer 必填）活着；`/api/extract/reviewers`（审定人从系统账号选）活着。`doclib_rule_detail` 实测 review_state 分布：**待审 26 / 采纳 7 / 驳回 7**。
- 明细审定：`POST /api/extract/details/{id}/review`（采纳前有「列没对齐不许采纳」硬闸）活着，同样无 UI。
- **采纳→写 rule 表：0 条。** `into_onto=0`；`/api/onto/summary` 实测 adoptions={采纳:0}、adopted_rules=0。规则表 82 条全部 `created_by='asset_loader'`（装载脚本从 规则清单_v0.1.json 播种，实测 TR-D1-01 status=draft、created_at=2026-10-27 13:08 即最近一次装载）。采纳入库的通道（`/api/onto/adopt`，含三硬闸：未裁决冲突不许采纳/四项必须人填不给默认值/软规则不许标禁止）在后端完好，但它原来挂在已删除的 RuleOnto.vue 上。
- 结果：四步工作流的第三步「审定→入库」在现在的界面上**没有落点**。工程师要么调 API，要么规则库永远停在装载脚本的 82 条。

### 1.3 规则冲突标注现状（客户投诉的调查结论）

客户原话指向的「冲突标注」在系统里有**三个不同的实体**，现状分别如下：

**A. 规则详情页的关系表（客户当场点的那个）。** RuleDetail.vue「与其他规则的关系」表（L163-184）：列=关系/对方/需裁决/缺口/说明。实测库里 exactly 18 条 rule_relation：overrides×6、priority_over×10、**conflicts_with×2**（TR-D3-12、TR-D4-16，均 needs_confirm=true）。这两条的 `note` 字段是完整 JSON（实测取回）：含 `with`（对方出处，如「制度 第十条 / 要点 2.1.20」「解答 解答4」）、**`their_text`（对方原文全文）**、`resolution`（暂定结论）、`why`（裁决依据）、`gap`（G-16/G-11）。
**问题一：整行没有任何可点元素**——无头实测关系卡内 a/button 数=0，「需业务侧裁决」warning tag 是死标签；`other_rule` 列显示的是「制度 第十条 / 要点 2.1.20」这种非规则节点字符串，不是链接。
**问题二：note 列把 JSON 原文截 200 字当文本显示**（MarkText 渲染 `{"with": "制度 第十条...`），their_text/resolution/why 全都埋在里面没被结构化呈现，更没有并排对比。
也就是说：**客户要的两条原文，数据 100% 已经在库里，缺的只是那个抽屉。**

**B. 多源口径冲突台账（doclib_conflict，真正的「抽取入库时标冲突」）。** 表结构（迁移 0020）：conflict_id/group_key/kind（阈值不一致|控制类型不一致|适用范围不一致）/detail/left_clause/right_clause/state（待裁决|已裁决|已忽略）/resolved_by/resolution。生成链路：`/api/onto/run`（三 Agent 统一口径，确定性、不出网）→ `group_and_detect` 按主题词×控制对象归并 → `_diff` 按**同单位数值/控制类型词/职级组织维度**比对 → 落 `doclib_conflict`；裁决 API `POST /api/onto/conflicts/{id}/resolve` 完整（已裁决必须写结论+署名，已忽略不复活）。检测器的防误报设计很有水平（单位分桶、控制词两类只能占一边、组>8 条承认判不了）。
**现状：表是空的。** 实测 `/api/onto/conflicts` n=0、`/api/onto/groups` n=0（doclib_rule_source 空表）——上一轮统一口径的产物在后来的装载/重置中清掉了，而**没有任何 UI 入口再跑一次**（旧 RuleOnto.vue 的「口径冲突裁决」区含 裁决人输入框+裁决结论输入框+已裁决/忽略按钮，git 历史可查，10-27 被删）。注意：旧版也只有 detail 文字串 + 两个按钮，**从来没有过左右原文并排对比**——客户要的东西在旧版里也不存在，这次是补做不是回滚。

**C. 抽取草稿 vs 现有规则的重复/冲突检测：不存在。** 现有防重只在采纳瞬间（`adopt` 查 onto_adoption 是否已采纳过同组）；新抽出的草稿与规则库 82 条之间没有「疑似重复」标记。客户说的「规则相同/冲突时系统会有标注」，在 B 有（跨文件口径冲突）、在 C 没有（草稿 vs 库内规则）——C 恰是最贴近「上传的规则入库时」的那个场景，要在方案里补。

## 二、分支细节清单（现状 → 顶级产品怎么做 → 建议 → 后端）

### 2.1 冲突对比与裁决（客户投诉的完整方案，最重）

**现状**（详证见 §1.3）：数据三处都有、呈现三处都断。A 场景 rule_relation.note 里连对方原文 their_text 都备好了；B 场景 doclib_conflict 有 left_clause/right_clause 双条款号+类型化 detail；C 场景（草稿 vs 库内规则）无检测。

**顶级做法**：用友 BIP 费用云的规则冲突处理是「冲突工作台」模式——冲突列表按业务域分组，每条冲突打开左右分栏对照（我方口径/对方口径，含制度原文引用），差异字段自动高亮，裁决动作内嵌（以我方为准/以对方为准/合并），裁决人+理由+时间全留痕，裁决后冲突边在关系图谱上变色。SAP GRC 的规则冲突检测（SoD 冲突矩阵）同理：**冲突的价值不在标出来，在于让人在 30 秒内看懂分歧在哪一格、拍板、并留下「谁拍的板」。**

**建议方案（控件级）**：

1. **统一交互容器：右侧抽屉 `a-drawer` width=1080，placement=right，mask-closable=false**。不用 Modal 的理由：内容=两栏原文+差异表+裁决表单，超一屏需要滚动，Modal 盖死全屏后没法对照背后的规则详情；抽屉可留 340px 页面上下文。抽屉内分四段（自上而下）：

   - **段① 冲突概览条**（高 48px，flex）：`a-tag` 冲突类型（阈值不一致=orange / 控制类型不一致=red / 适用范围不一致=blue / 口径冲突=red）＋ 归并组名（B 场景）或规则对（A 场景）＋ 影响提示文字（薄 API 计算：「两条均在执行集，裁决将改变在途单据口径」/「对方尚未成为规则」）＋ 缺口号 tag（G-16）。
   - **段② 左右并排原文栏**（grid: 1fr 1fr，各栏内滚动，max-height 40vh）：
     - 左栏标题「本条规则」：rule_id（`router-link` 跳详情）＋规则名＋控制类型 tag；**来源条款引用块**（浅灰底 quote 样式：文件名 code 样式＋条款号＋原文 text＋confidence tag——原生文本=green / OCR=orange）；判定逻辑按 KV 展开（非裸 JSON）；生效期、责任部门一行小字。
     - 右栏标题「对方」：分两种——对方是规则（拉 `/api/asset/rules/{other}` 同构展示）；对方是「制度 第十条」类非规则节点（A 场景实测值）：显示 their_text 引用块，**并加薄 API 反查 doclib_clause 拿全文正文与 OCR 可信度**（按文件名+条款号匹配，匹配不到如实标「原文未入库」）；B 场景直接按 left_clause/right_clause 两 id 取条款全文。
     - 数值差异高亮：两侧原文中的**冲突数值**（40 元 vs 50 元）用 `<mark>` 黄底标出——数值由薄 API 返回（复用 `_nums_by_unit` 的单位分桶逻辑，返回每侧 {值,单位,位置}），前端只做标记不做解析。
   - **段③ 差异对照表**（`a-table` size=small，三列：要素 | 左 | 右）：按八要素逐行比对（阈值/控制类型/适用范围/例外四类必比，其余相等则合并为一行灰字「其余要素一致」）；差异行左侧 3px 橙色竖条＋单元格内红字标注（`50 元` vs `40 元`）。判定逻辑为 JSON 时按 key 展开 KV 再比，不做字符级 diff（无意义且噪声大）。

2. **入口三处**（都是把已有标注变可点）：

### 2.2 抽取草稿的审定体验（并排：条款原文 vs AI 抽取结果）

### 2.3 规则版本历史

**现状**：rule 表主键就是 (rule_id, version)，多版本基础设施在；但实测 82/82 全是 version=1，无任何 UI 显示历史，也没有「修改规则→写 version+1」的动作（改规则的唯一途径是重跑装载脚本，还会把 created_by 不是 asset_loader 的规则之外全删——loader L97）。RuleDetail 页没有历史卡；created_at 是装载时间不是业务维护时间。

**顶级做法**：SAP 的 change documents / 用友的规则变更日志：一条规则的每次变更（谁、何时、改了哪个要素、为什么、依据哪个制度变更），逐版本可回看、可对比、可回滚到旧版；且「规则改了」要和「发布版本」联动（一条规则的 v2 只有随某次 release 发布才生效）。

**建议**（三步走，POC 只做前两步）：
1. **只读历史卡**（P1）：RuleDetail 加「版本历史」卡——薄 API `GET /api/asset/rules/{id}/versions`（SELECT 全版本+release_item 关联「v2 随 rs-xxx 发布」）；空态如实显示「仅 v1（装载基线，2026-10-27）」。同时把 release_item 的 change 字段（added/modified/retired——实测接口已回）在工作区 diff 里点得开：点「修改 3」列出是哪 3 条规则改了什么（快照对比，两端数据都在）。
2. **修订动作**（P1 后半）：`POST /api/asset/rules/{id}/revise`（body=八要素变更+理由+署名）→ INSERT version+1 新行（旧行不动，天然留痕）＋op_log；修订产生后工作区 diff 的 modified 才会非零，发布页的「与当前生效版本的差异」才真正有内容可讲。**修订必须给理由**——与驳回/裁决同一条纪律。
3. **版本对比视图**（P2）：抽屉内两版本八要素对照（复用 §2.1 的差异对照表组件——同一组件三种用途：冲突对比/草稿比对/版本对比，这是本次规划最大的组件复用红利）。

**后端**：薄 API 两个（versions 查询 + revise 写入），加 op_log；不动引擎（引擎按 effective release 装载快照，天然吃新版本）。

**建议**：

**后端**：薄 API 一个 `POST /api/extract/draft-from-chat`（复用 `ai_draft_one` 的模型调用与 number_check，只是 prompt 换成对话上下文；落库同 doclib_draft）。

### 2.5 异议收件箱（审核岗「我不认可这条命中」的回流侧）

**现状**：回流侧链路已通——ReviewReport 勾「我不认可这条命中」→ 提交时逐条写 `feedback_log`（metric=finding_vs_human, deviation_kind=false_positive, actual.rule_id，review.py L487-501，实测接口与 note 承诺一致）；**但规则管理员侧零呈现**：`/api/deviation` 的 false_positive_by_rule 只有 Deviation.vue（领导菜单）在用，engineer 菜单里没有偏差页；实测当前 by_kind=[null:667, needs_review_only:40]、false_positive_by_rule=[]（有回流通路、暂无存量异议）。规划文档里承诺的「规则审定·异议收件箱」未做。

**后端**：薄 API 两个（异议列表聚合查询 + 处置写入），全部 SELECT/INSERT，不动引擎。

### 2.7 规则试算（改规则先对历史单据预跑）

**现状**：不存在。发布工作区只有条数级 diff（新增 82/修改 0/退役 0——因为从没人改过），没有判定影响面。数据条件已备：69 张单（40 真实+29 演示）全量在库、`engine.load_ruleset()` 按 effective release 装载、`pipeline.run_cycle`/`audit_demo_bills` 可对任意单号跑规则链（不调模型）。

**顶级做法**：这是顶级规则引擎的标志性能力——SAP 的 simulation run / 用友 BIP 的规则试算：规则修改在沙盘上对历史单据（或样本集）重放，输出「将多命中 X 单/少命中 Y 单/结论翻转 Z 单」及逐单差异清单，签字发布前必看。**没有试算的规则修改等于盲签。**

**建议**：
- **P1（薄 API）**：`POST /api/publish/impact-preview`：对最近 N 张单（默认 30 天或全量 69，入参）分别用「当前生效规则集」与「工作区规则集」跑 `engine.evaluate`（纯内存判定，69 单×双版本实测口径预计 <2s，不调模型不出网），输出：按规则的 ±命中计数表（规则/版本A命中/版本B命中/差异）＋结论翻转单据清单（单号/旧结论/新结论/引起差异的规则）＋汇总条（结论不变 N 张、变严 M 张、变宽 K 张）。
- **UI 落点两处**：发布管理「工作区」冻结按钮旁加「试算差异」按钮（结果用抽屉显示，逐单行可跳报告页）；规则修订（§2.3-2）保存成功后 toast 附「去试算」链接。
- **口径纪律**：试算结果页必须写明「基于历史单据回放，不代表未来单据分布」；试算不写任何业务表（只读回放），但**写一条 op_log**（谁在发布前看了试算——签字发布的配套证据）。
- P2：试算支持指定样本集（如仅真实单/仅某主体），支持保存试算报告快照随 release 冻结（「这一版是基于哪份试算签的字」）。

**后端**：薄 API 一个（API 层组装双 ruleset + 调 evaluate；不改 engine——load_ruleset 本就吃库内任意版本数据）。红线核查：evaluate 是纯函数调用，属于「加薄 API」范畴。

### 2.8 制度文件更新 → 受影响规则提醒

**现状**：变化台账（新增/修改/消失）与文件级指纹都在（DocLib 变化台账页签）；`pending_extract` 能算「抽过之后又被改过的文件」；但**「这份文件改了，哪些规则受影响」没有出口**——后端 `asset.py get_doc` 的 referenced_by（按文件名 LIKE 反查规则）活着，可它挂在旧 asset 接口上，新 DocLib 页不调它；且 82 条规则里 41 条 source_clause.file 是类别代号（规则表/要点/制度），根本对不到文件（onto/cover 实测：有制度依据 19 / 编号对不上 22 / 来源未写明 41）。

**顶级做法**：政策变更影响分析（policy impact analysis）：新版制度文件进库→系统列出「引用旧版条款的规则 N 条」→逐条提示「该文件第 X 条已变更，请复核规则 TR-Dxx」→复核动作留痕。

**建议**：
1. **P1**：DocLib 变化台账的「修改」行加「受影响规则」列（薄 API：变化行 join referenced_by 同款反查，前端列显示 N 条＋点开浮层列规则链接）；「消失」行同理标「来源文件已不在库，N 条规则的原文链接受影响」。
2. **P1**（治理前提）：规则来源细化——onto/cover 的「来源未写明 41 条」不修，一切文件级影响分析都是漏的。建议随修订动作（§2.3）逐步补 source_clause 的真实文件名（客户待办 #4 规则溯源切片的同一条线），P1 先在 RuleDetail 来源条款区加「精确定位」编辑入口。
3. P2：文件新版进库且被引用条款指纹变化时，自动在受影响规则的 RuleDetail 顶部挂黄色横幅「来源文件已更新（2026-11-02），原文与起草时可能不一致」＋审定待办队列出现「复核 TR-Dxx」条目。

**后端**：①受影响规则反查薄 API（复用 get_doc 的 LIKE 逻辑挂到 doclib changes 出口）；②文件×条款级反查（source_clause.file+clause 对 doclib_clause）。

### 2.9 规则生效期到期预警

**现状**：rule 表有 effective_from/to（实测 TR-D1-01：2026-01-01 ~ 空=长期）；无任何预警 UI；也无「过期规则是否还在执行集」的口径说明。

**顶级做法**：政策有效期管理：临期（30/7 天）分级预警、过期自动退出执行集或标灰、报表按生效期审计「哪些单据是在规则过期后仍按旧标准审的」。

**建议**（P2，POC 量级小）：规则清单加「生效期」列（from~to，临期橙字/过期红字删除线）；规则库顶部统计条加「30 天内到期 N 条 / 已过期 N 条」卡（数字来自列表接口实时算，不写死）；过期规则的详情页加横幅。暂不做「自动退出执行集」（引擎行为不动，红线）——只在资产面预警，处置走修订/发布。

**后端**：零（列表接口已回 effective_from/to，实测确认）。

### 2.10 规则与附件决策表的一致性

**现状**：lookup_row 自带 must_hit/must_not_hit/conflict 对账标记与 reconciliation（源表行数 vs 归并行数）；报销标准页签坏了所以全不可见（§2.6）；规则侧 `external_table` 字段记录规则引用哪张决策表（实测表结构有），但没有「表改了哪些规则受影响」的反查。

**顶级做法**：决策表与规则的双向台账：改表前预览影响规则；改规则时提示其依赖的表与最近变更。

**建议**（P2）：报销标准页签（§2.6 修复后）的表行编辑动作（如有）前置影响预览；RuleDetail 的 external_table 值改为可点（跳报销标准页签并定位该表）。后端零（数据都在）。

## 三、知识图谱可视化专章（用户新增需求：酷炫+粒子+可下钻+可对比+可溯源）

> 用户原话背景：「之前那一版的 demo 给规则操作员做了三个本体，每个本体都有一个图谱可视化。那个功能得留着，只是前端要酷炫一点，带粒子效果。比如规则跟规则之间的对比关系，数据可下钻等等。数据可对比、数据可溯源，这些都要做到。」

### 3.1 现状盘点（旧实现与现存资产）

- **旧前端已删、git 全量可考**：`git show 683cb71~1:前端/src/pages/BizOnto.vue`（四页签：建立/展示/关系/图谱；图谱=SVG 圆周等分布局，确定性渲染，两次打开一模一样）与 `RuleOnto.vue`（本体建设/展示/关系/图谱；其注释明确图谱的存在理由：「图谱不是关系表的美化版，它回答表格回答不了的问题：哪个节点是枢纽、哪条边悬着、哪个点是孤的」）。10-27 死代码退役时随五页物理删除。
- **后端完好**：`GET /api/onto/graph` 实测可用——17 实体（E01 degree=10 是枢纽、带 concepts 计数与 gap 计数）/ 18 实体关系边 / 18 规则关系边（overrides×6、priority_over×10、conflicts_with×2，needs_confirm 布尔随边返回）；api.ts 的 `ontoGraph()` 封装仍在（1698 行）。
- **当前无任何挂载**：KnowStruct.vue（知识结构页）只调 ontology/process，**不调 ontoGraph**——图谱功能目前零 UI。
- **数据面三个缺口**：①实体节点带 rules 计数（实测 rules=null——出口没填）②无规则↔概念引用边（rule_concept 表有数据但 graph 接口不回）③无命中热度（粒子要承载的信息，review_finding 按规则聚合计数现成但没出口）。

### 3.2 定位决策

三个候选的权衡：

| 候选 | 优点 | 代价/风险 | 判定 |
|---|---|---|---|
| ① 规则库新增「关系图谱」页签 | 规则管理员（用户点名的角色）日常可见；演示动线顺（规则清单→图谱一跳）；与冲突对比抽屉同页联动 | 修正 IA「本体退出业务界面」——但用户本次原话「那个功能得留着」就是对新 IA 的修正指令 | **推荐** |
| ② 升级管理员知识结构页 | 不动 IA | 演示时切 admin 账号，动线断；用户明确说给规则管理员 | 否 |
| ③ 独立「知识图谱」菜单 | 入口显赫 | 破坏「角色菜单≤6 项」纪律；与规则库割裂 | 否 |

**建议**：方案①——规则库第四页签「关系图谱」（RulesLib tabs：规则清单/报销标准/规则明细/关系图谱），engineer 角色专属；KnowStruct 保持技术只读不动（避免双处维护同一可视化）。文案口径：页签名用「关系图谱」不用「本体图谱」（术语映射表纪律：本体一词不进业务界面），页内副题「规则、概念与制度的关系全景——点节点看详情，框两个规则做对比」。

### 3.3 技术选型对比

| 维度 | ECharts 5（graph+lines，Canvas） | AntV G6 5.x | ECharts+GL | 原生 Canvas+D3-force |
|---|---|---|---|---|
| 粒子效果 | **连线粒子流动原生支持**（lines 系列 effect：trailLength/symbol/period）；节点呼吸用 emphasis+动画循环 | 无内置流动粒子，需自定义渲染插件 | 有（GPU 粒子系统） | 全手写（含 requestAnimationFrame 循环） |
| 下钻交互 | click/hover/legend 事件模型够用；tooltip 强 | **最强**：内置 activate-relations、combo 折叠、fisheye、16+ behavior | 同 ECharts | 全手写 |
| 大数据量 | Canvas 渲染 1k 节点流畅；force 布局可预计算 | 同量级更优（webgl 可选） | 最大 | 取决于手写质量 |
| Vue3+AntD 融合 | 无官方 Vue 封装但接入极简（ref+resize observer），社区成熟 | 同左，文档偏 TS | 同左 | 最简 |
| 离线可用（npm 本地打包） | ✅ 按需引入 | ✅ | ✅（但需 WebGL） | ✅ |
| 体积代价 | **按需（graph/lines/tooltip/legend+CanvasRenderer）约 +250KB min / +90KB gzip** | 全量约 +600KB min / +230KB gzip，按需裁剪空间小 | echarts 之上再 +600KB+ | 最小（d3-force ~30KB）但人力成本最高 |
| 演示环境风险 | 低（Canvas 2D，RDP/虚拟机稳） | 低 | **高：POC 服务器 192.168.106.141 经 RDP 访问时 WebGL 常走软件渲染掉帧** | 低 |

**推荐：ECharts 5 按需引入 + Canvas 渲染器，否决 echarts-gl。** 理由：①粒子诉求里最核心的「连线粒子流动」是 ECharts lines-effect 的原生能力，G6 5 反而要自定义；②体积代价最小且可按需控制；③Canvas 2D 在 RDP 演示环境零风险（GL 的软件渲染掉帧会在客户现场翻车，这条一票否决）；④交互深度（下钻/对比/路径高亮）在 100 节点量级上手写事件完全可控，G6 的 behavior 优势要到 500+ 节点才兑现。项目现依赖仅 ant-design-vue——新增 echarts 一个依赖，体积 +90KB gzip，可接受并在方案中明示。

### 3.4 交互设计（控件级）

**一图三层，不是三张图。** 业务/规则/流程三本体**合成一张可切换层的图**（规模仅 17+82+15 节点，拆三图反而碎）：顶部分层切换 `a-segmented`（全景 / 规则层 / 概念层 / 流程层），实现=series 过滤+legend 联动，数据一次拉全。

**粒子承载信息（不是纯装饰）**：
- **节点呼吸**：规则节点外圈光晕强度 ∝ 该规则近 30 天命中次数（数据源：review_finding 按 rule_id 聚合，薄 API 出口加 hit_count；实测 TR-D4-02 recent_findings 满 10 条——热门规则一眼可辨）。零命中的规则静态灰节点。图例注明「光晕=近 30 天命中热度」。
- **边粒子**：关系边上的流动粒子方向与速度表达「覆盖/优先于」语义（overrides 边粒子从覆盖方流向被覆盖方）；**conflicts_with 且 needs_confirm 的边红色虚线+脉冲**（最醒目的动画留给最需要人处理的东西），点击即开 §2.1 冲突对比抽屉。
- 节点配色：控制类型双态（禁止=红/警告=橙，与全站 CTRL 色一致）；概念节点蓝绿；孤点（degree=0）灰+虚线圈（旧版图谱注释的「孤点要人看」语义保留）。

**数据可下钻**（三级）：
1. 点**规则节点** → 右侧抽屉（720px）：八要素摘要+来源条款原文引用块+可执行性三态+最近判定 5 条（全部复用 `/api/asset/rules/{id}` 出口，与 RuleDetail 同数据源）；底部「查看完整详情」链接。
2. 点**概念节点** → 抽屉：概念定义+可得性+**引用它的规则清单**（rule_concept 反查，薄 API 加一个出口）+所属实体；可得性非绿的显示缺口号与白话说明。
3. 点**边** → 关系详情浮层：关系类型中文+双方节点摘要；conflicts_with 边的浮层带「对比裁决」主按钮（冲突对比抽屉的第二入口）。

**数据可对比**（用户点名「规则跟规则之间的对比关系」）：
- 图右侧「对比栏」：点任一规则节点的「+加入对比」，或图上 ctrl+click 两个节点 → 两节点间**路径高亮**（BFS 最短路，图仅百余节点前端算）+ 其余节点降透明度 0.15；
- 对比栏内嵌 §2.1 的**差异对照表组件**（八要素逐行左右比对）——无 conflicts_with 关系的两条规则也能比（例如 TR-D4-05 vs TR-D4-10 谁更严），这是冲突对比之外的「任意对比」模式，正是用户说的「规则跟规则之间的对比关系」；
- 对比结果可「转为裁决」（若确属口径冲突，一键生成 doclib_conflict 记录走裁决流——把「发现冲突」从被动等检测变成主动人工发起，薄 API）。

**数据可溯源**：
- 节点 hover tooltip：规则节点显示「TR-D4-05 住宿费超标准 · 来源：《差旅管理实施细则》第二十条（原生文本）」——source_clause 三要素直接进 tooltip；
- 边 hover：关系依据（priority_over 的 note、裁决记录 resolved_by/at）；
- 概念节点 tooltip 显示「出自哪个实体、当前可否取到」；
- 抽屉内来源条款引用块带「查看文件」链接（跳制度文件页定位该文件——文件名到 file_id 的映射薄 API）。

### 3.5 性能与扩展路径

当前规模（17 实体+82 规则+18+18 边+约 60 概念 ≈ 200 节点）对 Canvas 无压力。扩展三招按序启用：
1. **聚合（combo）**：规则按维度 D1~D10 折叠成 combo 气泡（显示「D4 交通费 12 条 · 命中 45」），双击展开——规则破百后默认聚合态；
2. **LOD 缩略**：缩放级别低于阈值时概念节点收进所属实体（度数小的先收），hover 展开局部；
3. **布局缓存**：force 布局结果存 localStorage（图拓扑指纹变化才重算），保证「两次打开一模一样」的确定性（旧 SVG 圆周布局的这条优点要继承——确定性是排障对照的前提）。
数据出口层面：graph 接口加 `?layer=` 参数避免一次性回全量子图（P2 再做，当前量级不需要）。

### 3.6 排期归属与薄 API 清单

单列 **P1-G**（不挤占原 P1 条目）：薄 API 扩展 4h（onto/graph 出口加 hit_count/concept-edges/rules 计数三字段+概念反查规则出口+文件名映射出口）＋ ECharts 引入与图组件骨架 8h（分层切换/布局/图例/暗色主题）＋粒子与呼吸动画 4h ＋ 三级下钻抽屉 5h（复用 RuleDetail 数据出口）＋ 对比模式与差异表组件复用 4h ＋ 调优与无头断言 3h ＝ **约 28h**。差异对照表组件由 §2.1 P0 统一产出，此处只消费。

## 附：本文引用的关键既有设计判断（方案明确不推翻）

1. 抽取两档制：自动给草稿、人工确认才落本体，没有自动发布这条路。
2. 冲突只发现不选边；裁决必须记 resolved_by；「已忽略」也留行（防反复提示）。
3. 有未裁决冲突的归并组不许采纳（硬闸非提示）；软规则不许标禁止。
4. 采纳≠进规则库≠发布生效，三道闸各自独立；发布必须签字（ck_release_signed），发布与生效是两件事。
5. 托管可写、引用只读；删除托管文件三道闸（引用拒删/产出 409+purge 出路/登记行按消失保留）。
6. 「同名另存」与「同内容已存在」是相反的两件事，状态、颜色、文案都不许合并。
7. effective_release 全站唯一定义（三级阶梯），页面与引擎共用。
8. 「判不出」是独立档位不许二分；条款号对不上≠查无依据。
9. 数值幻觉核对只查阈值不查所有数字（防红标失效）；OCR 数值不进硬阈值。
10. 引擎层一行不动：本方案全部薄 API 均为 API 层查询/组装/出口映射，evaluate 调用属只读回放。
