### 1.2 提交复核后：队列真减？已办可查？留痕可溯？

**结论：合格（一处口径小瑕疵）。**

- 队列真减：实测 58→57，刷新/换机不回弹（manual=none 是服务端口径，ReviewReport.vue L54 注释即此设计）。
- 已办可查：MyWork「已办记录」（按 manual_review.reviewer=当前账号姓名归集，review.py L405-417）；报告页「复核记录」卡合表人工留痕 + AI 轮次，按时间倒序。
- 留痕可溯：manual_review（谁/何时/何结论/理由/不认可清单）+ disagree 逐条回流 feedback_log（finding_vs_human/false_positive，review.py L493-501，cycle_id 为空时如实报 0 不假报成功）+ 审计追溯页 F 段。

### 1.3 40 真实单误报 / 漏报现状

**结论：当前零误报、零漏报（有反馈回路的单），但这是「几乎没人工结论可比对」下的零，不是检出能力的证明。**

- `/api/deviation` 实测：`by_kind = [null:667, needs_review_only:40]`，false_positive_by_rule 为空。无一条 false_positive / false_negative。
- 原因：40 张真实单全部 conclusion=review（命中 0、待人工 2~6 项），人工已复核仅 5 张且全是 agree——AI 没说「不通过」，人也没退回，两头都没产生偏差事件。
- **真实风险画像**（这是审核员每天实际要看的东西，实测聚合 35 张未复核真实单的待人工规则分布）：

  | 规则 | 次数 | 待人工原因（实测原文） |
  |---|---|---|
  | TR-D6-03 | 35/35 张 | 单次连续出差天数算不出（缺 OA 起止日期，缺口 G-04），伙食补助只能倒算累计天数 |
  | TR-D6-06 | 35/35 张 | 同上，且连带否掉交通费/伙食/市内交通三项的判定 |
  | TR-D1-02 | 19 张 | 有住宿费但住宿发票未 OCR 入库，无法核对抬头 |
  | TR-D6-05 | 18 张 | 交通费凭证缺往返行程信息 |
  | TR-D1-03 / TR-D4-02 / TR-D4-06 | 5/4/4 张 | 零星 |

  **解读**：真实单的「待人工」集中在**数据缺口**（票据未 OCR、OA 未同步），不是规则判定模糊。也就是说，审核员对真实单的复核动作今天大多是「凭票面人工核」，系统给的增量价值是「告诉你哪几项它核不了」。演示单（29 张）才是规则命中能力的展示面（reject 8 + review 14）。这个事实决定了 P1 里「待人工项引导」比「更多规则」更值钱。

### 1.5 性能

**结论：清单层不卡（虚拟滚动达标），但翻张单次 716~913ms 偏慢，瓶颈在串行 API 链。**

实测数据（1440×900，本机）：

| 指标 | 实测值 | 说明 |
|---|---|---|
| 队列全量拉取（58 张） | reject 1 请求 363ms + review 1 请求 580ms | 每页 200 一页装下；万张场景才需服务端分页（前端已封顶 50 页） |
| 页面首载到首张可交互 | 2387ms | 含队列 2 请求 + 首张报告 2 请求 + 附件 N 张 |
| 翻张单次（5 次采样） | 903 / 913 / 877 / 716 / 897 ms | max 913ms |
| 单张报告 `/api/reviews/{id}` | 213ms | 快 |
| 单张详情 `/api/bills/{no}` | 464ms | 慢（一次查 6 类子表） |
| 附件原图单张 | 94ms / 119KB PNG | 可接受 |

翻张的网络瀑布（实测抓包，一次 ArrowRight）：

```
+0ms   GET /api/reviews/{run_id}          ← 报告（213ms 内回）
+212ms GET /api/bills/{no}                ← 等 reviews 完成才开始（loadAll 串行 await）
+813ms GET /api/bills/{no}/reviews        ← 历次审核（与 manuals 并行）
+813ms GET /api/bills/{no}/manuals
+817ms GET /api/attachments/1912/file     ← 缩略图 3 张并行
+819ms GET /api/attachments/1913/1914/file
```

**瓶颈定位**（代码 ReviewReport.vue L87-93 `loadAll`）：`await api.review()` 完成后才 `await api.bill()`，两个无依赖请求被串成 900ms 链。并行化 + 邻张预取（翻到第 N 张时预取 N+1 的报告）可压到 300ms 内。这不改任何后端。

1366×768 低分屏实测：无横向溢出、队列栏 320px / 主区 766px、body 不滚、复核通过按钮 y=279 在一屏内。布局合格。

## 二、分支细节清单（顶级产品怎么做 → 我们的差距 → 建议）

每条按「现状 → 顶级做法 → 建议方案 → 后端」四段写。后端一栏「薄 API」指可在 review.py 这类 API 层加，不动引擎。

### 2.1 对比视图：申报值 vs 制度规定值并排

**现状**：证据在展开行里，是一维 KV 列表（`住宿费:600 / 住宿上限:400 / 住宿标准:200 元/人·晚 / 住宿晚数:2 / 人数:1`）。数字都在，但审核员要自己在脑子里做「600 > 400」这道减法。命中 message 里有文字结论（`住宿费 600.0 元超过上限 400.0 元（200 元/人·晚 × 2 晚 × 1 人）`）但没有视觉化的并排对照。

**顶级做法**：Concur Expense 的 exception detail 是两栏表——左「Submitted」右「Policy」，超标行红底显示差额与超出百分比；汇联易在超标项旁直接给「超出 ¥200（+50%）」徽章。判定成本从「读一段话」降到「扫一眼红字」。

**建议**：在 ReviewReport 证据展开区内加**对比块**（仅 hit 且 evidence 里同时存在「实际值键 + 限额键」时渲染，由后端在 evidence 里按约定键对输出——现成的素材已经在了）：
- 结构：`| 项目 | 单据申报 | 制度规定 | 差异 |` 四列，差异列自动算金额差与百分比，超标红字 `+200.00（+50%）`。
- 键对约定：evidence 已有 `住宿费/住宿上限`、`本单金额/阈值`（TR-D10-06）、`伙食标准/伙食补助费` 等成对出现（实测采样确认）。后端薄 API 在 `/api/reviews/{id}` 的 finding 上加一个 `compare: {label, actual, limit, unit}` 数组（从 evidence 按规则元数据映射，映射表放规则 logic 里由规则管理员维护，不写死在前端）。
- 落点：`ReviewReport.vue` 展开行 `.ev-grid` 左栏顶部，判定证据 KV 之前。

**后端**：薄 API（review.py 出口组装 + 规则 logic 加 compare 映射声明；不动判定逻辑）。

### 2.2 回看上一张

**现状**：三重断链。①提交后自动跳下一张，被提交单移出队列，队列栏里**再也看不到它**（manual=none 口径，这是立页设计不能破）；②MyWork 已办记录链接去单据详情而非报告页（实测 href 确认）；③报告页没有「最近处理」历史。审核员想检查「刚才那张是不是点错了」，只能去 Workbench 筛 manual=done 再找到单号再进报告页，五步以上。

**顶级做法**：Gmail 发送后的「撤销发送」+ 「已发送」文件夹；Concur 审核历史就在当前队列下方，点击即回看当时的判定快照。

**建议**：
1. **提交后的轻量「撤销/回看」条**：提交成功 toast 从 600ms 延长到 5s，附「查看刚才的单」链接（runId 已在手，`nextTarget` 逻辑同款）。成本极低。
2. **队列栏底部加「最近处理」折叠区**：本会话已提交的单（sessionStorage 记最近 20 条 runId，纯前端），点击直达报告页（报告页对已复核单显示锁定闸门 + 复核记录，本身已支持，实测直达 FJPG-BX2610090441 的报告 200 正常）。
3. MyWork 已办记录加第二列链接「报告」与单号并列（`run_id` 已在 my/work 返回里，前端补一个 router-link）。

**后端**：不需要（runId 直达报告页的通道已存在且实测可用）。

### 2.3 相似单据参考

**现状**：无此能力。实测确认：`/api/bills` 只有 conclusion/is_demo/q/claim/manual 五个过滤参数，无按主体×金额×时间窗聚合的接口；报告页无任何「相似单」入口。真实数据里有素材——同主体（财智分公司 40 张全同主体）同金额组合 4 组（如 1147 元 ×3），TR-D10-06 已在引擎层做「2 日内同主体同收款方」聚合（peer_bills_2d，拆单检测），但这个 peers 数据只用于判定、不暴露给审核员。

**顶级做法**：Concur 的 duplicate detection 直接在异常列表显示「与单据 XXX 相似度 92%」，点击并排比对；汇联易报销时同酒店同日期自动提示历史价格。审核员查「这张是不是重报」是这个岗位的高频动作。

**建议**：分两步。
1. **P1（薄 API）**：报告页闸门下加「同类单据」折叠卡：`GET /api/bills/{no}/peers?window=7d`——同主体 + （同金额 或 同收款方 或 业务类型相同）在 N 日内的单据列表，含各自 AI 结论与人工结论。SQL 与 TR-D10-06 的 peer_bills_2d 同构（expense_bill 自联，纯查询）。审核员自己比对。
2. **P2**：peers 里带 diff 摘要（金额差、明细行差），前端并排两栏。

**后端**：第 1 步薄 API（纯 SELECT，不动引擎的 peer_bills_2d 判定，独立查询同口径数据）。

### 2.4 意见模板（常用意见一键填）

**现状**：复核意见、退回理由都是空白手打（实测确认无任何模板机制；退回理由必填——每次退回都要现编一段话）。

**顶级做法**：Concur 的 approver comments 是可管理的短语库（个人 + 组两级），输入框带自动补全；退回理由按原因分类（缺材料/超标/非合规用途），分类本身进入报表维度。意见模板的价值不只是省打字——**它把退回原因结构化了**，后端「偏差与回流」页才能按原因聚合。

**建议**：
1. 退回理由弹窗加**原因分类下拉**（缺附件 / 超标准 / 信息有误 / 疑似重复 / 其他——五类起步，选项存规则资产或配置表，不写死前端）+ 分类对应的常用话术快捷选择（`a-select` + 下方 tag 行，点选追加到 textarea）。**分类字段随 manual_review 落库**（加一列 `return_category`，迁移脚本），偏差页就能按退回原因出分布。
2. 复核意见（agree_with_note）加同款下拉，可选「无备注」默认空。
3. P2：个人常用语管理（存用户偏好表）。

**后端**：薄 API——manual_review 加列（只加不改）、退回接口接收 category、偏差页查询补维度。话术库用规则资产的 yaml 或独立小表，不进引擎。

### 2.5 退回后的闭环（报账人改完重新提交）

**现状**：**这是当前模型最大的概念缺口，但 POC 阶段如实标注比假装闭环更诚实**——现有链路没有「报账人重新提交」的入口（数据源是客户 xlsx 批量导入），退回的终点是 manual_review 一条 return 记录 + 偏差统计。重跑审核会生成新 review_run（同 bill_no 多轮，BillDetail「历次审核」表已按轮次列出），但**没有「新版本单据」语义**（金额改了会被新 run 重新判定，旧行不变；审核员在新 run 报告页能看到历史轮次，却没有「上一版判了什么、这次改了什么」的对照）。

**顶级做法**：Concur 的 returned expense 会回到提交人的 inbox，修改重交后审计线完整保留（v1 → v2 → v3），审核员界面有「查看变更」diff（哪些字段改了）。

**建议**（POC 内诚实做法）：
1. 报告页对「该单历史上有 return 记录」的单，在闸门上方加**黄色提示条**：「本单曾于 {日期} 被退回（{原因分类}），本次为重报」——数据已有（billManuals 按单查全历史，实测接口在）。
2. 历次审核表（BillDetail 已有）加**前后结论对照列**：v2 行显示与 v1 的命中差异（`+TR-D4-14 / -TR-D1-02`），数据从两轮 findings 比对，纯展示层。
3. 正式版路线图（写进方案但不做）：报账人端入口 + 单据版本表（bill_version），迁移 0045 系列已证明台账只增不改的模式可复制。

**后端**：第 1/2 步薄 API（billManuals 已有，diff 是前端或出口层比对 findings）。

### 2.6 大额 / 敏感单视觉分级

**现状**：队列筛选有「大额」（≥1 万，前端写死阈值）、Workbench KPI 卡有「大额待审」，但**队列行本身无金额也无大额标识**——队列行只显示单号 + 演示 tag + 命中数（实测 DOM）。队列按「风险」排序时 250 万的演示单和 847 元的真实单长得一样。

**顶级做法**：分级审批线（amount banding）是行业标配：超阈值单进不同审批流，UI 上用色带/徽章区分；Concur 的 spend limit 超限单有专属 flag 与排序加权。

**建议**：
1. 队列行补**金额列**（右对齐、tabular-nums，`qrow` 现有 44px 行高可容纳）；≥阈值（阈值从后端配置取，当前前端写死 10000 是违例——数字不写死红线）加 `大额` 徽章 + 行首 3px 橙色竖条。
2. 阈值来源：薄 API `GET /api/review/config` 返回 `{big_amount_threshold, ...}`（或挂在现有 status 接口），规则管理员可改。
3. 实测提醒：当前队列大额 5 张里 3 张是演示单（250 万/120 万/110 万），真实单大额仅 2 张（1.8 万/1.4 万）——分级上线后演示效果主要靠演示单，真实单的大额线建议在方案里向客户说明按其真实分布调阈值。

**后端**：薄 API（一个配置出口；若阈值要按主体差异化则是 P2）。

### 2.7 会话中断（审到第 30 张刷新/换电脑）

**现状**：**进度与上下文全部在后端，恢复能力合格**（这是 manual=none 服务端口径设计的直接收益）：刷新后队列重新拉取、已办不回弹（实测）；换电脑登录同账号，队列口径一致。缺的是**「回到我上次看的那张」**——免参进入总是跳队列首张（`loadQueue` 里 `pickQueue(queue.value[0])`），第 30 张刷新后落回第 1 张，要重新翻 29 次。

**顶级做法**：Concur 的 queue 记住 last viewed item；Gmail 记住上次展开的会话。

**建议**：登录账号 + 当前 runId 存 localStorage（`fjhy:last-run:{account}`），免参进入时若该单仍在队列中则 replace 到它而非首张；不在队列（已被别人审掉）则回落首张并 toast 一句「上次处理到 {单号}，该单已有复核结论」。纯前端，30 行内。

**后端**：不需要。

### 2.8 附件体验（放大看票面）

**现状**：缩略图 110px + 点击大图（实测 64ms 打开、728×996、Escape 关闭）。**大图无缩放、无旋转、无翻张**——`max-width:100%; max-height:76vh` 的静态 img。审「住宿发票抬头」要读 14px 的票面字，76vh 下票面细节是否可辨取决于扫描件原始分辨率（实测单张 119KB PNG，分辨率尚可，但拖不动放大镜就是硬伤）。另外三张附件的缩略图在翻张时全量加载（瀑布实测 3 张并行 817ms）。

**顶级做法**：Concur 的 receipt viewer 支持缩放/旋转/全屏、键盘翻页；发票 OCR 产品（网易企微汇财等）标配放大镜与局部框选。**审核「发票对不对」的最后一米就是票面可读性。**

**建议**：
1. 大图层加**滚轮缩放（0.5×~4×）+ 拖拽平移 + 旋转按钮 + ←/→ 翻本单附件**（翻张与大图翻附件不冲突：大图层激活时 ←/→ 归附件，Esc 关层后归还队列）。CSS transform 实现，无需引库。
2. 大图层底部加附件切换条（当前 2/4，文件名），与发票要素（若有抽取字段）并排显示——`attachment_extract_fields` 已抽过 A01/A03/A04/A05 的文字/日期字段，读图时对照系统抽出的抬头/日期，正是「AI 抽取 vs 人眼复核」的演示亮点。
3. P2：命中证据反向锚定附件——TR-D1-02 命中某张住宿发票时，证据区给「查看该发票」直链（evidence 里已有发票号，薄 API 按 run_id+rule_id 反查 attachment id）。

**后端**：第 1/2 步不需要；第 3 步薄 API（finding×attachment 关联查询）。

### 2.9 命中解释口径对非技术审核员是否友好

**现状**：两处硬伤（实测截图确认）：
1. **表格 msg 列裸露 markdown 星号**：`但本条要的是**单次连续**出差天数`——`**` 原样显示在表格里（td 用的是纯 span，没用 MarkText 组件；同页的 excluded 行倒是用了 MarkText）。实测确认 `表格内是否裸露 ** 星号: true`。
2. **术语墙**：TR-D6-03 的 pending 理由直接写「缺口 G-04」「TR-D6-06 连带否掉三项」——G-04 是内部缺口编号，审核员不知道那是什么；规则号互引适合管理员视图，不适合办理页。展开区里有制度依据原文（这部分做得好），但「这条规则核不了对**我**意味着什么、我该去看什么」没有行动指向。

**顶级做法**：Concur 的 exception 文案三段式：什么被违反（引制度原文）→ 检测到什么（数据事实）→ **建议你核什么**（action item）。第三段是给审核员的，前两段是给审计的。

**建议**：
1. msg 列换单位统一用 MarkText（全局组件已注册，零成本）。
2. 展开区证据块底部加**「人工核点」一行**（视觉：蓝底浅色 info 条）：由规则的 pending_reason/hit message 配套输出（数据源=规则 logic 里加 `human_check_hint` 字段，规则管理员维护，如 TR-D1-02 → 「请打开住宿费发票核对：①抬头是否为核算主体全称 ②金额与明细住宿费是否一致」）。存量规则可先由薄 API 提供默认文案（按 control_type 与 evidence 键生成），有维护后再覆盖。
3. 「缺口 G-04」类内部编号在审核岗页面脱敏为「系统暂缺 OA 出差审批单数据，无法自动判定」（映射表出口层转换；管理员的规则详情页保留原编号）。

**后端**：第 1 步纯前端；第 2/3 步薄 API（出口层文案映射，规则资产加字段）。

### 2.10 待人工项的「人工判断」动作本身有没有引导

**现状**：没有。35 张真实单 × 平均 3.4 个待人工项，展开看到的是「判不了的原因」，然后呢？——闸门只有通过/退回两个钮，**对「待人工项逐项表态」没有任何收口**。审核员实际的复核路径是：展开 → 自己看票 → 直接整体通过。每个待人工项既没有「已人工核实」的勾选，也没有「这一项我核实为无问题/有问题」的分项结论。后果：①AI 判不了的东西，人审过后**不留任何分项痕迹**，审计时说不清单子里哪几项是人核过的；②偏差回流的粒度只有整单（conclusion_vs_human），finding 级回流只有「不认可命中」这一个负向通道。

**顶级做法**：分贝通/汇联易的人工复核清单（checklist）模式：每个待人工项是一个可勾选的核实项，可勾「已核实无问题」「核实有问题（转退回）」「跳过」，全部勾完才能提交整体结论；勾选结果落库成为 finding 级人工结论，与 AI 结论逐项比对形成真正的 finding_vs_human 回流。

**建议**：这是**专业感提升最大的一条**，分两步：
1. **P1**：展开区「我不认可这条命中」勾选旁，加对偶的正向勾选「**已人工核实**」（对 hit 与 pending 都可用）。提交时随 disagree_with 一起传 `verified: [rule_id...]`，薄 API 落 manual_review.agree_with 或新列 verified_rules（JSON 数组）。报告页复核记录里显示「人工核实 2 项：TR-D1-02、TR-D6-03」。**注意与既有判断的衔接**：agree_with 字段语义是「明确认可的命中」，verified 是「人工已核实」——建议复用 agree_with 语义扩展而非加第二套勾选，避免两套「认可」口径打架（这正是 review.py 注释里「agree_with 不许塞文字」的同一纪律）。
2. **P2**：闸门加「待人工 0/3 已核实」进度提示（不强制拦提交——强制会拖慢老手，提示引导新手）。

**后端**：薄 API（manual_review 既有 JSON 列可承载，或加一列；回流统计补维度）。

### 2.11 附：我补充分支细节（5 条）

**A. 队列的演示/真实混排与免参首张**

实测：风险排序下，reject 组 8 张全是演示单排最前，review 组里 10 张有命中的演示单也压过 35 张真实单——**审核员每天打开审核报告页，前 18 张全是演示单**，真实工作（40 张真实单）从第 19 张开始。这既是演示需要（首屏展示命中能力）也是日常噪音。建议：队列栏筛选器加「数据口径」三态（全部/仅真实/仅演示——「仅真实」已有 `real` 选项但藏在下拉里），并把**上次选择的筛选条件存 localStorage**（会话恢复的变体）。首张策略与客户现场确认：演示给领导看用默认全量，审核员日常用「仅真实」。

**B. 翻张时左侧队列当前行可视性**

实测 58 张时当前行会自动滚进视野（watch cur 的 scrollIntoView 逻辑在）。但**当前行在筛选视图与全队列的位次口径**（「第 X / N 张」用全队列位次）在筛选时会让进度条看起来跳跃——这是设计注释里明确的取舍（口径不变），保留，仅在 P2 加个 tooltip 说明「进度按全队列计」。

**C. 复核人输入框的必要性**

现状：复核人 input 每次预填登录人姓名但**可编辑**（实测可改）。既有判断「署名跟会话走，不许有第二个来源」（ReviewReport.vue L183-188 注释）与可编辑 input 自相矛盾——改个名字就造出第二个署名来源，且 manual_review 存的是姓名字符串（my/work 按姓名归集，重名即串档）。建议：改只读展示（登录人姓名 + 不可改），或保留 input 但提交时以会话姓名为准（input 仅作显示别名）。涉及真实风险（留痕真实性），建议 P0 处理：**展示改只读**。

**D. 已办记录「未署名」历史数据**

实测 5 条真实单历史留痕 reviewer 全是「未署名」（2026-10-25 回流功能上线前后的过渡数据）。MyWork 已办按姓名归集，这 5 条不属于任何人，实际不可见（chenfang 的已办=0）。建议：薄 API 一次性数据订正（按 claim/操作日志线索回填）或在 my/work 里给管理员可见的「未署名」兜底视图。POC 演示前建议直接订正——客户看到「未署名」会问住。

**E. 退回理由弹窗的「理由将进入偏差统计」口径**

弹窗文案「原因将进入偏差统计」——实测当前退回并不自动生成 feedback_log 偏差事件（只有勾「不认可」才写 finding_vs_human；整单 return 与 AI 结论的比对 conclusion_vs_human 依赖偏差页作业，见 deviation 接口 kinds 说明）。文案承诺了统计去向但链路是断的（或至少是延迟的）。建议：要么在提交 return 时由薄 API 同步写一条 conclusion_vs_human/false_negative 候选（若 AI 结论为 pass/review 而人退回），要么把文案改成「原因将记录在复核留痕中」——**承诺了就是欠着**（此项目自己的纪律）。
