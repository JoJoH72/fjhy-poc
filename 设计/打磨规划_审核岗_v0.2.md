## 二、v0.2 新增 / 升级条目

### A-P0-1 逐条异议文字意见（客户 #2 的审核岗侧半条，P0）

- **背景**：客户排期表 #2 本期工作原文「支持标注异议并填写个人修改意见」。现状 `disagree_with` 是纯 rule_id 数组（`服务端/app/api/review.py` L652），审核员勾了「不认可」说不出为什么；退回分类意见是整单口径，不能替代逐条意见。规则管理员侧的异议收件箱（规则管理员 v0.2 的 B-P0-1）点开异议要看到的就是这句原话——A线不产字，B线收件箱就是空壳。客户节点 11-11。
- **标准依据**：五环第 4 环（回流数据要能被处置人读懂——只有 rule_id 的回流无法处置）；标注可下钻（B线侧点开异议 → finding 原文 + 审核员理由）。
- **交互方案（控件级）**：展开区「我不认可这条命中」勾选框右侧，勾选时就地展开 `a-input`（size=small，maxlength=100，placeholder「选填：一句话说明原因」）；取消勾选立即收起并丢弃草稿（与「意见当场清空、只属于本次提交」纪律同源）；提交后 toast 文案不变。键盘流不受影响（onKey 已判 tagName，输入框内不劫持）。逐条意见不进报告页复核记录的正文展示，只在 B线收件箱明细里出现（避免报告页信息密度上升）。
- **后端薄 API**：零新端点、零表变更——`review.py` manual_review 的 disagree 回流处（L686-689）把 note 并入 `record_feedback` 的 actual JSON（`actual={"rule_id":…, "note":…}`，`服务端/app/audit/recorder.py` L220 的 actual 本就是 JSON dump）。`manual_review` 落库的 disagree_with 保持数组形态不动（复核记录显示口径不变，历史行天然兼容无 note）。
- **工时**：3h（前端 1.5 / 后端 0.5 / 自测 1）。
- **优先级**：P0。依赖方向：B线收件箱消费它，但不阻塞——收件箱先上聚合与处置，note 字段有则显示。

### A-P0-2 教学句残留清剿·审核岗两页（客户 #7 收尾，P0）

- **背景**：客户 #7「全站页面文案统一替换为通用易懂用语」。C线已完成 12 页清剿与禁用词断言，C线汇报清单确认残留集中在 6 页，其中审核岗侧 2 页：ReviewReport、MyWork。
- **标准依据**：文案纪律（标题只许名词短语、教学句/自述句清零、术语全站统一）；执行基准为 `设计/产品企业级化总体规划_v0.1.md` §5-G 术语映射表。
- **交互方案**：无结构改动，纯文案层——逐句替换为名词短语或收进 tooltip；「缺口 G-04」类内部编号在 A线侧维持白话映射（v0.1 P0-7 已建出口映射，核查残留路径）。
- **后端**：零。
- **工时**：2h（含禁用词断言脚本对这两页的豁免口径复核）。
- **优先级**：P0（M2 文案通俗化的收尾，10-29 口径）。

### A-P1-1 compare 映射声明进规则 logic（v0.1 P1-2 收尾，P1）

- **背景**：对比块四列（申报/制度/差异/徽章）已上线，但键对映射目前在出口层按 evidence 键名推断兜底——v0.1 原设计是「映射表放规则 logic 由规则管理员维护，不写死在前端」。推断兜底遇到键名不规范的规则会静默失配（该条不渲染对比块，用户无从知道为什么）。
- **标准依据**：「数字不写死」红线的同族——结构映射同样不许锁死在出口代码里；规则资产归规则管理员维护（B线修订动作是编辑面）；单实体单入口（compare 声明只在规则资产里定义一次，出口与前端都只消费）。
- **交互方案**：A线无新交互，展示不变。数据契约：`rule.logic.compare = [{label, actual_key, limit_key, unit}]`；出口组装顺序 = 声明优先 → 键对推断兜底 → 都没有则不渲染（维持现状）。为两条高频规则（TR-D4 住宿、TR-D10 大额）补声明作为种子。
- **后端薄 API**：`review.py` 出口读声明（规则装载兼容缺省）；编辑面在 B-P1-C（修订动作）的表单里带 compare 声明四字段——A线先定契约落库，编辑面随后补。
- **工时**：4h（契约与出口改造 2 / 种子声明 1 / 自测 1）。
- **优先级**：P1。与 B-P1-C 同一迭代交付。

### A-P1-2 BillDetail 大图层复用（v0.1 P1-3 后半，P1）

- **背景**：ReviewReport 的附件大图已有缩放（0.5×~4×）/ 旋转 / ←→ 翻张；BillDetail 仍是静态大图（`fileUrl` 直链 img，`前端/src/pages/BillDetail.vue` L42）。审核岗从 Workbench / AIReview / MyWork 进单据详情看附件时体验割裂——同一动作两种交互模式。
- **标准依据**：交互模式业内标准与全站统一（同一动作同一模式）；四态齐备（大图层加载失败给原因 + 重试，不许白框）。
- **交互方案**：把大图层抽成 `前端/src/components/ImageViewer.vue`（props：attachments、初始 index；emit：close），ReviewReport 与 BillDetail 同款挂载；BillDetail 缩略图点击进入，Escape 关闭；键盘 ←→ 在层内翻附件（与队列翻张不冲突，层关闭后归还焦点）。
- **后端**：零。
- **工时**：4h（组件抽取 2 / BillDetail 接线 1 / 断言 1）。
- **优先级**：P1。**顺序硬约束**：与 B-P0-2（附件改判接线）同改 `BillDetail.vue`，必须串行——B-P0-2 先（客户项），本条后；或合并给同一实施 agent 一次做完，禁止两线并行改此文件。

### A-P1-3 翻张 559→300ms（v0.1 P0-6 深度版：渲染链，P1）

- **背景**：并行化 + 邻张预取后翻张 559ms，v0.1 的 300ms 目标未达。网络瀑布已消除（reviews/bills 并行、邻张预取），剩余瓶颈在渲染链：翻张触发队列列表重渲 + 证据展开区全量重建 + Async 包装层的重复请求。
- **标准依据**：五问第 1 问（页面为高频路径让路——翻张是审核岗最高频动作，58 张/天；更关键是打断节奏感）。
- **方案（按实测定位后三选一或组合）**：①邻张报告数据预取进 SWR 缓存（Async 已 SWR 化，翻张命中缓存 = 纯渲染）；②队列行组件 memo 化（cur 变更不重渲 58 行，只换高亮）；③主区 key 稳定化，避免整树重建。**验收断言**：无头浏览器连续 5 次 ArrowRight 采样，单次耗时 max < 350ms（含渲染，网络命中缓存口径）。
- **后端**：零。
- **工时**：6h（含性能采样断言脚本，扩展 `var/e2e-review.cjs`）。
- **优先级**：P1。独立条目，无依赖，任何窗口可做；建议避开 B线合入周（回归基线稳定时测）。
