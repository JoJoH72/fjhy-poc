## 0. 基准声明与四项决策（2026-10-24 用户已确认）

| # | 决策项 | **已定** | 随之而来的约束 |
|---|---|---|---|
| **Q1** | TR-D6-01（必要附件完整性） | **只出警告不拦截** | must 项缺失 → `outcome=pending`（待人工）+ `control_type=警告`，**绝不进 reject**。optional 缺失照旧不出任何信号。齐套清单正常渲染 |
| **Q2** | 真实单重跑审核 | **重跑，并出前后对比** | 重跑前后各留一份实测数字（执行/命中/待人工/结论分布）。这是 P0 的第一件事，也是后面所有 UI 改动的数据前提 |
| **Q3** | UI 风格基准 | **保持现有朴素 CSS** | 只搬 Demo 的交互设计，**不引入 Ant Design**。统计卡、批量条、缩略图预览全部用现有 `--brand/--hit/--pend/--pass` 变量和手写 CSS 实现 |
| **Q4** | 附件审核落位 | **单据详情页内** | **不动 `navTree.ts`**、不加二级菜单。链路进度与成本面板挂到 `AIReview.vue` |

**Q1 的连带影响**：本文 §3.2 原写「must 缺失可拦截」，按此决策改为「must 缺失出警告、转待人工」。决策表 YAML 表头那条纪律（must 可拦截 / optional 绝不拦截）是**规则资产层面的能力**，本次演示的**启用口径**是降一档——两者不矛盾，但页面文案必须按启用口径写，不能照抄表头。

参照关系：`Demo`（福建港口集团）是**参照资料**，不是基线。基线仍是 `fjhy-poc-baseline` 的六条。本文凡引用 Demo 的做法，都只借交互设计，不改本项目的规则口径、字段命名、菜单顺序。

### 2.2 不搬的 2 点

- **验收看板里的静态写死数字**（`BENCH_ROUNDS` 三轮 47/47 全写在前端常量里）。本项目的口径是数字一律取自后端实测接口；写死的数字一旦和库里不一致，就是在页面上说假话。要做看板就从 `/api/ai-review/status` 取。
- **中英文混杂的状态值**。Demo 里 `judgement/judgment` 拼写不一致、severity 显示英文原值，它自己的 `docs/UI优化计划.md` 把这两条列为 P1 bug。本项目的 `CONCL` 映射已经是中文，别退回去。

### 2.3 Demo 在附件上恰恰是最弱的一环

Demo 的附件只有 `SubjectDetail.tsx` L605-629 一块：`Image.PreviewGroup` 缩略图墙 + 文件名 + `doc.kind` 徽章，抽取结果另放一个 Collapse（L632-670）。**附件和规则之间没有任何连线。**

本项目的 `BillDetail.vue` 附件块反而更强：有类型/把握/来源/出处、有「判类型」按钮、有大图展开、有「申报张数 vs 真实原图」双指标并列。**所以附件这一块不是抄 Demo，是在现有基础上往前做一步。**

## 3. 附件审核设计

### 3.1 一张附件要能回答三个问题

审核岗看一张附件时的真实动作是：**这是什么 → 上面写了什么 → 它让哪条规则过了或没过**。现在页面只答了第一个。

```
┌─ 附件 3/4 ──────────────────────────┬──────────────────────────────────┐
│                                     │ ① 这是什么                        │
│                                     │   住宿费发票  把握 高  读图判定   │
│                                     │   依据：票面标题「福建增值税专用  │
│         [ 原图 · 可缩放 ]           │         发票」+ 住宿费明细行      │
│                                     │                                   │
│         ◀ 上一张    下一张 ▶        │ ② 上面写了什么（读图抽取）        │
│                                     │   开票日期  2026-09-25   高 ✓已回写│
│                                     │   备注栏    9.25-9.27 林** 中 ○台账│
│                                     │   发票类型  增值税专用发票 高 ✓   │
│                                     │   凭证形式  电子           高 ✓   │
│                                     │   ⚠ 金额/税额本轮不抽（10-22 决策）│
│                                     │                                   │
│                                     │ ③ 它参与了哪些规则                │
│                                     │   TR-D7-03 住宿发票开票时间  ✗命中│
│                                     │     开票 09-25 < 出差首日 09-28   │
│                                     │   TR-D3-04 应为专票且信息完整 ✓过 │
│                                     │   TR-D6-03 出差2天以上需住宿票 ✓过│
└─────────────────────────────────────┴──────────────────────────────────┘
```

**③ 是全新的东西，也是「附件审核」四个字的落点。** 技术上要加一张反查：`review_finding` → 它用到的 `attachment_id`。实现路径见 §5 的 P1-3。

### 3.2 必要附件齐套性：把决策表画出来

客户问「AI 怎么知道附件齐不齐」，答案就是那张 29 行的决策表。把它渲染成清单，比任何文字解释都快：

```
┌─ 必要附件齐套性（TR-D6-01）─────────────────────────────────────────┐
│ 业务大类 CL002  国内差旅费 ／ 小类 CL002001  市内交通费              │
│ 口径来源：必要附件决策表 v0.1 第 7 行（场景表「业务域」153 行去重）   │
│                                                                      │
│ 必要附件（must，缺失出警告、转待人工 —— 2026-10-24 决策：不拦截）    │
│   ✓ A01 出差审批单        → 附件 1  [看原图]                         │
│   ✓ A02 差旅费明细表      → 附件 2  [看原图]                         │
│   ✓ A03 交通费报销凭证    → 附件 3、4  [看原图]                      │
│   ✗ A04 住宿费发票        → 缺                                       │
│                                                                      │
│ 个性化附件（optional，缺失不拦截、不告警）                           │
│   ○ A08 租车合同或协议    → 缺（仅实际租车时适用）                   │
│                                                                      │
│ ⓘ A01/A02 在场景表原文写作「出差审批单/差旅费明细表」，斜杠含义       │
│   未定（且／或），现按 any_of 建模并标 needs_confirm（G-25）。        │
│   若实为「两者都要」，这一项会在 28 行里全部漏报。                   │
└──────────────────────────────────────────────────────────────────────┘
```

三条必须写在页面上，否则这块会被误读：

1. **must 与 optional 分区显示、配色不同**。混在一起会把 41%（29 行里 12 行带个性化附件）的正常单判成缺件。must 用 `--pend`（警告色）而不是 `--hit`（不通过色）——按 Q1 决策它不拦截，配色不能让人以为拦了。
2. **「缺」与「还没判」是两种状态**，不能都显示成 ✗。现在 219 张全判完了，所以暂时没有「还没判」——但重新抽取、新上传附件之后会再出现。
3. **斜杠口径未定的那条要挂提示**，别让人以为系统已经确定了。

### 3.3 规则 ↔ 附件双向跳转

`ReviewReport.vue` 现在的证据表是纯 key-value（`evidenceRows`）。审核岗看到「住宿费发票开票日期 2026-09-25 早于出差首日 2026-09-28」的第一反应是**我要看那张票**，现在要退回工作台 → 点单据 → 滚到附件 → 找哪张 → 点开，五步。

改成：证据来自附件的 finding，证据表下面直接挂 **缩略图 + 「看原图」**，点开就地放大。一步。

### 3.4 附件审核链路的进度与成本

实测 `classify calls 246 / failed 25`、`extract calls 351 / failed 24`——**49 次失败，页面上一个字都没有**。这是真出网真计费的动作，失败必须看得见（和 `AIReview.vue` 已经做到的「大模型辅助」面板同一条纪律）。

建议新增一页（或 `AIReview.vue` 加一块）：

```
┌─ 附件感知链路 ───────────────────────────────────────────────────┐
│ 判类型   219/219 ✓      调用 246 · 失败 25 · token 218,385      │
│ 抽字段   197/197 ✓      调用 351 · 失败 24 · token 333,042      │
│          回写 195 / 抽出 197（2 条把握不到「高」，只落台账）     │
│                                                                  │
│ 类型分布  A03 132 ████████████  A04 32 ███  A01 28 ██           │
│           A02 22 ██  A05 5 ▌                                     │
│ 把握分布  判类型：高 221（全部）                                 │
│           抽字段：中 205 · 高 116 · 低 6                         │
│                                                                  │
│ ⚠ 49 次失败明细  [展开]   ← 失败原因必须能点开看                 │
└──────────────────────────────────────────────────────────────────┘
```

### 3.5 人工审核：补附件级意见

现在人工复核只有**单据级**（同意/同意并备注/退回 + 勾「我不认可这条命中」）。附件审核要加**附件级标记**：

- 每张附件一个状态：`未看 / 已核对 / 有问题`（有问题必填说明）
- 单据级的「同意」在还有附件处于「未看」时给提示（不拦，只提示）
- 附件级意见落台账，和 `feedback_log` 一样可回流

**为什么要这个**：多人、多轮复核时，「谁看过哪张票」现在完全说不清。客户提「附件的审核」，很可能问的就是这个——不是「AI 审附件」，而是「人在系统里审附件留不留痕」。**这一条属于 Q1 的延伸，口径请用户确认。**

## 4. 工作台与报告页的其他优化（搬 Demo）

### 4.1 `Workbench.vue`（122 行 → 约 260 行）

- 顶部补统计卡一排：全部 / 未审 / 通过 / 待复核 / 不通过 / 真实·演示（数取自 `/api/bills` 的 banner 与分页 total，**不在前端写死**）
- 表格加勾选 + 批量操作条：批量同意 / 批量退回（退回必填理由，沿用 `ReviewReport.vue` 的校验）
- 加一列「附件」：`n 张 · 类型已判 n/n`，点击直达单据详情的附件块
- 整行可点进详情（Demo 的 `onRow`），不用非得点单据号

### 4.2 `ReviewReport.vue`（236 行）

- **人工复核面板从页底提到页首**（Demo A3）。现在要滚过「结论/命中/待人工/未执行/通过折叠」五块才看到闸门，而它才是这页存在的理由
- 命中/待人工/通过/不适用**合成一张表**（Demo A4），用 outcome 列区分，默认按 命中→待人工→通过→不适用 排序。四处分开看不出「一共查了什么」
- 证据来自附件的挂缩略图（§3.3）
- 提交后显示**人工复核记录**（Demo A7），不是只留一句「已记录」

### 4.3 `AIReview.vue`（448 行）

- 加 SDAFI 分步进度（Demo A6）。一轮约 5 分钟，现在全程只有「审核中…」三个字；S/D/A 三阶段在后端是分开的，进度可以真实上报，不用假动画
- 「智能审核」按钮旁加一行：**本轮会不会带附件事实**。重跑之前，这一行写「上一轮（10-18 06:56）跑的是无附件快照，执行 12/82」——否则没人知道为什么重跑

## 6. 明确不做

- **不写死任何前端常量数字**（Demo 的 `BENCH_ROUNDS` 式看板）。数一律走接口。
- **不把「申报张数 ≠ 真实附件数」做成规则**。实测 34/40 不等（申报多 32、少 2），口径没定之前这会是一台 32/40 命中的误报机。两个指标并列显示，谁也不覆盖谁——`BillDetail.vue` 现有做法保持。
- **不在 optional 附件缺失上出任何告警**。决策表表头的纪律，页面必须照做。
- **不改规则编号、控制类型、菜单顺序**。参照 Demo 只借交互，不动基准。按 Q4，`navTree.ts` 这一轮一行都不改。
- **不引入 Ant Design**（Q3）。Demo 的 `Image.PreviewGroup`、`Table rowSelection`、`Steps` 这些组件要用现有手写 CSS 重做一遍，样式变量沿用 `style.css` 里已有的那套。
- **TR-D6-01 不进 reject**（Q1）。must 缺失只出 `pending` + 警告，页面文案和配色都按「不拦截」写。
- **不统一剥离接口原文里的 Markdown 强调符**（见 `fjhy-backend-markdown-frontend-plaintext`）。新增的展示文本走 `MarkText` 渲染。
