## 一、Users 用户与角色（admin）

**五问作答**
1. 用户/路径：admin 管账号；最高频=加人/停用/重置密码，全部在首屏工具栏与行内操作位 ✅
2. 交互模式：标准双栏（左角色列表+右页签）业内定式 ✅
3. 五环逐环：新增（表单+错误就地显示）/停用（开关受控翻转，失败回弹）/删除（双重确认+历史留痕说明）/重置密码（loading+后果提示）/保存角色（内置角色禁用+原因）✅
4. 四态：账号表拉取失败有错误条不静默（P0-2 已修的路径实测在）；空角色有人数对照提示 ✅
5. 信息密度：左栏「N 人 · M 个菜单」一眼扫清 ✅

**实测证据**
- 停用 linjia（UI 开关）→ 落库 enabled=false + op_log「停用账号」留痕；linjia 旧会话**立刻** 401（user_by_token 每次查 enabled，不等 12h 过期）；再登录被拒且文案统一「账号或密码不正确」——**不泄漏「该账号已停用」**（防枚举口径，iam.py L114 注释宣示的纪律实测成立）。
- 重名账号（账号=linjia）被拒，提示「账号 linjia 已存在」，未落半截。
- admin 自身：启用开关禁用（noSelf 护栏）；角色详情保存按钮禁用+「系统管理员为内置超管，权限不可修改」原因说明。
- 埋点核对：iam.py 全部 7 个写动作（新增/修改/启用/停用/删除账号、重置密码、恢复默认+角色 4 动作）都有 op_log.log_by_request——口径立了且每个动作都埋了 ✅。
- OpLog 分类计数实测：登录（1793）/用户与角色（239）/复核（305）/规则（57）/发布（5）——数字全接口来，无写死。

**当场修**
- **V3-1（小，已修）**：重置密码弹窗的后果说明原只放在 input placeholder 里——输入开始后 placeholder 消失。已改：弹窗正文加 a-alert「重置后该账号的旧会话全部下线，需用新密码重新登录」，placeholder 只留输入格式提示（关键信息不进 placeholder——文案纪律）。

**进 v0.3**
- 无遗留。

## 四、KnowStruct 知识结构（admin）

**五问作答**
1. 用户/路径：实施与排障（只读声明置顶）✅
2. 与 RulesLib 图谱的分工：实测**不重复**——KnowStruct=三元结构技术表视图（概念/要素/节点三页签，纯表格），RulesLib 图谱=业务关系全景（ECharts 力导+命中粒子+冲突裁决入口）。同一批概念数据两种形态，定位不同 ✅
3. 四态：三页签数据全接通（业务概念 15 行/规则要素表/流程节点表）✅
4. 术语豁免：页面实测**无**表名/接口名级技术标识符泄漏（sys_user/review_finding 等 0 命中）——比豁免口径预期还干净，断言脚本无需为此开豁免 ✅

**实测证据**：业务概念 15 行带可得性标签（黄=仅单人可得/需票据OCR 2 行）；缺口列（gap_id）3 行有值。

**进 v0.3**
- **V3-3（中）**：**概念缺口行不可下钻**。gap_id 是裸文本（G-xxx），点击无响应——「这个缺口是什么、影响哪些规则」要跑去数据接入要求单文档找。标注可下钻纪律对技术页同样成立：gap_id 可点 → 浮层显示缺口说明+受影响概念清单（数据在本体 YAML 的 gaps 段，加薄出口即可）。
- **V3-4（小）**：三页签之间无联动（点概念不联动规则要素）。技术页可不做，但「被规则引用数」列（n_rules）是数字却点不到对应规则——可点跳 RulesLib 图谱定位该概念节点，形成 admin→engineer 的排障动线。
